# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

OneKeyFishing is a World of Warcraft addon for **WoW Forever** (Interface `16001`, build 1.60.1, `WOW_PROJECT_ID = 18`), published under the MIT license. The Forever client runs the modern (Mainline) API, not the Classic one. The game client can run in any language, so game data is matched **by ID, never by name**. The addon's own interface is in ten languages (English is the base; see `docs/languages.md`); every visible text goes through `ns.L` (see Localization and Locales below).

**English is the development language.** Code, identifiers, comments, documentation (`README.md`, `docs/`, `specs/`, `CHANGELOG.md`, this file), commit messages, branch names and pull requests are written in English, whatever language the conversation with the author is in. The only exceptions are the translations themselves (`Locales/<code>.lua`) and language names written in their own language (as in `docs/languages.md`). No tool enforces this; it is on whoever writes the text.

Hard rule: the addon must stay within Blizzard's UI Add-On Policy. Every game action (cast, hook, use item) happens on a real key press through secure buttons and override bindings. No automatic reaction to the bobber splash, no external tools.

Docs: `README.md` (players), `CHANGELOG.md`, `docs/ROADMAP.md` (future features), `docs/shared-db-plan.md` (the shared catch database in four releases; specs per release in `specs/`), `docs/publishing.md` (release steps and the policy checklist), `docs/languages.md` (supported interface languages, how a language is chosen, rules for translation files), `docs/checklists/` (in-game checklists of features, e.g. `interface-language.md`, `catch-database.md`), `docs/history/` (finished plans: `mvp-plan.md` with the API spike results, `publishing-plan.md` for 1.0.0).

## Commands

The addon lives in `OneKeyFishing/` (exactly what goes into `Interface/AddOns`: the TOC, Lua files, `Bindings.xml`, `Locales/`, `UI/`); `tools/`, `tests/`, `docs/` and project files stay in the repository root. Paths below such as `Core.lua` or `Locales/enUS.lua` are inside `OneKeyFishing/`. The tools need Node.js 18+ (`npm install` once):

- `npm run check`: the addon folder holds only packaged files (TOC-listed + `Bindings.xml`), Lua 5.1 syntax, undeclared **and unused** globals against `.luacheckrc`, lines up to 120 characters, ASCII-only Lua/TOC/XML files (except the translation files `Locales/<code>.lua` other than `enUS.lua`), no `SetFont` call in the addon (the game's font objects pick a Korean, Chinese or Cyrillic font when needed), Lua files only in `OneKeyFishing/` and `tests/` (test files get the syntax and line-length checks), every repository root entry either packaged or listed in the `.pkgmeta` `ignore` list, every Lua file listed in the TOC, locale keys in sync, the bundled seed `SeedData.lua` (at most 1 MB, the `ns.SeedData` fields, place keys), and `package.json` version == newest `CHANGELOG.md` entry; it also lists the open `VERIFY` markers. Run it after every change. A new WoW API global goes into `.luacheckrc` `read_globals`.
- `npm test`: the Lua tests in `tests/` and the Node tests `tests/*_test.mjs` (they export `tests`, a list of `{ name, fn }`; used for `tools/harvest.mjs`) (`npm test -- lures` runs only matching files). `tests/run.mjs` runs every `tests/*_test.lua` in a fresh fengari state after `tests/wow.lua`, which holds the WoW API stubs (frames, events, a controllable clock and timers, configurable bag item counts, cooldowns, prices, loot) and the helpers (`test`, `eq`, `near`, `fire`, `advance`, `tick`, `click`, `load_addon` (with an optional step before the login), `load_files`, `fish_cast`, `catch_cell`). Unknown globals are permissive stubs. Run it after every change; add or extend a test when changing logic that can run without the game (Core, Bags, Catch, Stats, the statistics window). fengari is Lua 5.3, the game is 5.1: keep the addon free of 5.1/5.3 differences, and fix a test that fails only because of 5.3 in the test or the stub.
- `npm run dev`: packages the working folder into `dist/OneKeyFishing/` and `dist/OneKeyFishing-<version>.zip` (version `x.y.z-dev+<commit>`).
- `npm run build`: refuses uncommitted changes, runs check and test, then packages the last commit; it also refuses while any `VERIFY` marker is left.
- Verification debt: code built on an assumption that only the game can confirm (while the game cannot be played) carries `-- VERIFY(<id>): <what>`, with the assumption, its fallback and the way to check it in the feature's `verification.md`. `npm run check` lists the open markers; a marker is removed only after the author confirms the behaviour in game.
- `npm run link` / `npm run unlink`: link `Interface/AddOns/OneKeyFishing` to `OneKeyFishing/` (a junction on Windows) for development without building; the unbuilt version shows as `dev`.
- `npm run harvest`: before a release, turns the catch data of every account under `WOW_ADDONS_DIR` (plus saved files given as arguments; they are parsed, never executed) into `OneKeyFishing/SeedData.lua`, the seed bundled with the release. Accepted contributions are kept in `seed/contributions.json` (repository only) by `<id>@<epoch>`, so the same input never counts twice, and a run without new sums leaves the seed and its epoch alone; `-- --reset <mapID>` counts a map only from the newest game version on (after a patch that changed its catch); `-- --synthetic 3000` writes a random seed for a load test (never commit it). Format and rules: `specs/002-local-catch-db/contracts/`.
- `npm run install-addon`: `dev`, then copy into the game's AddOns folder. `link`, `unlink` and `install-addon` read `WOW_ADDONS_DIR` from the environment or a git-ignored `.env` (see `.env.example`), and refuse anything that is not `.../Interface/AddOns` or that contains the repository. A new file or a TOC change needs a game restart, not just `/reload`.
- The package contains only the TOC, the files it lists and `Bindings.xml` from `OneKeyFishing/`, plus `LICENSE`, `README.md` and `CHANGELOG.md` from the root (`tools/addon.mjs`). `## Version: @project-version@` is filled in at build time; `package.json` holds the version. The release packager replaces such keywords (and strips `--@debug@`-style blocks) in **every** packaged file, so addon Lua and XML must not contain them (`npm run check`); an unbuilt addon is recognised by the version starting with `@` and shows `dev`.
- Branches: work happens on `develop`; `main` holds released code and changes only by merging `develop`. Push to `develop`, never directly to `main`.
- Releases: a pushed tag equal to the version (`1.0.0`) on a `main` commit runs `.github/workflows/release.yml` (BigWigsMods/packager with `.pkgmeta`, whose `move-folders` makes `OneKeyFishing/` the package; the root files land in the same folder, so `ignore` leaves out everything but `LICENSE`, `README.md` and `CHANGELOG.md`). The release stops while `CHANGELOG.md` has a `## [Unreleased]` heading.
- Claude cannot run the game, so in-game testing is always handed to the user with a checklist. In game: `/okf` lists commands; `/okf debug` shows the state report used in bug reports.

## Architecture

All files share the addon namespace (`local _, ns = ...`). Load order is the TOC order; a module may only call another module at runtime, not at file load time, unless it comes earlier in the TOC.

- **Localization.lua** (loaded first): `ns.L` (keyed by the English text; the effective translation, then English, then the key), the registry `ns.AddTranslation(code, nativeName, fill)`, `ns.GetLanguages()` (menu order), `ns.ResolveLanguage(preference, clientLocale)` and `ns.SetLanguage(code)`. Core resolves the language in `ADDON_LOADED`, the first point where the saved preference (`settings.language`, `"auto"` or a code) exists. **No `L[...]` lookup may run while the files load** (at file scope, in a table built at load): it would be stuck in English. Build such texts at runtime instead; `ns.earlyLookups` and `tests/locale_test.lua` catch a load-time lookup.
- **Locales/enUS.lua**: the English list. Every `L["..."]` in the code must be listed there and vice versa (`npm run check`). Use literal keys only (`L["text"]`, never `L[a .. b]`) and keep color codes outside the strings. Every other `Locales/<code>.lua` (listed after `enUS.lua`, before `Core.lua`) registers a complete translation through `ns.AddTranslation`; `npm test` checks completeness and placeholder order, so a new English text needs its nine translations in the same change. Languages, the language setting and the file rules are in `docs/languages.md`. Not localized on purpose: the debug report, slash commands (names, help descriptions and the `/okf` help output), the addon name and the language names (constitution, Principle II).
- **Core.lua**: `ns.RegisterEvent` (several handlers per event), the internal message bus `ns.On` / `ns.Fire` (messages below), `ns.CreateButton` / `ns.FitButton` (the shared panel button, which grows to its text), `ns.CreateText`, `ns.ItemDisplay` (an item's link and icon), `ns.ShowItemTooltip` (item tooltip with the few-lots auction price), `ns.OpenRadioMenu` (a `MenuUtil` menu of choices), `ns.ShowPopup` (two-button popups), saved variables (`Migrate` runs `MIGRATIONS` up to `DB_SCHEMA`, then `ApplyDefaults` fills missing keys without overwriting; bump `DB_SCHEMA` and add a migration whenever a saved field is renamed, moved or reshaped), the slash command dispatcher and help (`/okf` and `/onekeyfishing`; the commands themselves are in Commands.lua), `ns.version` from the TOC, and binding labels. `OneKeyFishingDB` holds account-wide data (settings, fished item IDs, auction prices, positions); `OneKeyFishingCharDB` holds per-character data (fishing gear, statistics, and pending restore state).
- **Commands.lua** (loaded last): `ns.COMMANDS`, every slash command in one place, sorted by name, with its English description and a `run` function that calls the module at runtime (constitution, Principles II and VI). Modules register no commands; the names, descriptions and `/okf` help are English on every client.
- **Action.lua**: the single fishing key. Keys bound to `ONEKEYFISHING_ACTION` (Bindings.xml) are overridden only while the mode is on. When the player is not channeling, the key clicks `OneKeyFishingButton` (SecureActionButtonTemplate). Its `PreClick` resolves the action by priority: apply lure, then open a fished container, then cast Fishing. While channeling Fishing, the key is bound to `INTERACTTARGET` (soft-target interact hooks the bobber). The overrides are owned by a `SecureHandlerStateTemplate` frame whose `[combat]` state driver clears them inside combat. `Action.Enable` picks up a Fishing channel that is already running (`UnitChannelInfo`), because no `CHANNEL_START` comes for a cast begun before a `/reload` or before the mode was switched on. The keys are re-read on `UPDATE_BINDINGS` and after combat; our own overrides fire that event too, so it rebinds only when the keys changed.
- **Mode.lua**: enter and exit fishing mode. Every changed CVar, the gear swap, the camera zoom and a `resumeMode` flag are stored in the character DB *before* changing anything. As a result, exit, logout, `/reload` (which also fires `PLAYER_LOGOUT`) and crashes all restore correctly. After `/reload` the mode resumes after a 1 second delay, because bindings and the spellbook are not ready on `PLAYER_ENTERING_WORLD`; if it cannot resume (combat), the weapons come back at once and the rest of the gear and the camera after combat. Leaving in combat only sets a pending exit (weapons back at once, the rest after combat). While the mode is on, the plain binding body of the action key only runs when combat dropped the overrides, so `OneKeyFishing_ActionKeyIdle` says why the key does nothing.
- **Gear.lua**: equips the chosen pole (or the best pole by fishing bonus) plus user-picked extra items. It records only the slots it changed (`charDB.gearSwap`). On exit a slot is restored only if it still holds what the addon put there. The fishing bonus is parsed from tooltip lines that contain the client's localized Fishing spell name minus its first UTF-8 character (tooltips may lowercase it, and `string.lower` only handles ASCII). Weapons return immediately in combat; the rest waits until combat ends.
- **Bags.lua**: lures and fished containers. `FindLure` takes the best lure in the bags (`LURES`, best first) that is usable and not on its own cooldown (`C_Container.GetItemCooldown`, the global cooldown does not count); for lures passed over because of a cooldown it fires `LURE_READY` when the soonest one is ready. An attempt counts as failed only when, 8 s later, the pole has no lure and the lure is not on cooldown; a failed lure is skipped until fishing mode is entered again. `Bags.DescribeLures` feeds the debug report. A container's loot window is matched to the open attempt by the item GUID (`GetLootSourceInfo`); nothing is opened over an open loot window; a container whose loot did not fit waits for free bag space, a locked one is skipped for the session. `ns.ForEachBagItem` (Data.lua) is the shared bag iterator. Data.lua also has `ns.GameObjectID(guid)` (the object ID of a game object GUID; Forever scrambles the spawn part) and `ns.BOBBER_OBJECT_ID`.
- **Catch.lua** turns casts and loot into `FISH_CAUGHT` / `FISH_MISSED` messages (`FISH_CAUGHT` also says whether the loot came from a fishing pool: `ns.IsPoolLoot()`, a loot source GUID of a game object other than the bobber 35591); a cast without loot is settled as a miss 1 s after it ends, also when the next cast already started. **Stats.lua**, **UI/Toast.lua** and **Skill.lua** consume them. Stats counts time in segments (fishing mode on, optionally not AFK) and flushes them on zone change and logout. It keeps per-session, per-zone and total buckets and bumps `Stats.GetVersion()` on every change. `Stats.PlaceName(mapID)` is the "Zone - Subzone" name both statistics tabs show. A cast that runs across a `/reload` is recognised by its channel start time (`charDB.countedCast`) and not counted twice. The item value is computed at read time through **Prices.lua** (the higher of the vendor and the scanned auction price; an auction price based on fewer than 5 pieces or fewer than 3 auctions is shown with a "few lots" mark and not used for values). **Auction.lua** runs one `C_AuctionHouse.SendSearchQuery` at a time and stores the average unit price of the cheapest 20% of all listed pieces (results sorted locally; while the game reports more commodity results it asks for the next page, up to 5, each with its own wait and only when the server takes requests; later pages arrive as `COMMODITY_SEARCH_RESULTS_ADDED`; at a timeout the pages that came decide), with throttle retry and timeout; `Auction.CanScan()` is the one "can scan now" rule for every scan button.
- **SeedData.lua** and **CatchDB.lua**: the catch database (`docs/shared-db-plan.md`, `specs/002-local-catch-db/`). A place is `<mapID>:<range>:<cell>`: the map as `C_Map.GetBestMapForUnit` returns it, `min(4, floor(base rank / 75))`, and a 10x10 grid cell (`"x"` without a position). The place is read at every `FISHING_CAST_START` under Catch.lua's cast number (`ns.GetFishingCastID()`), and the cast that `FISH_CAUGHT` or `FISH_MISSED` names is settled. Every catch and miss goes into `OneKeyFishingDB.shared.mine` (lifetime, never reset) and the account's contribution record `shared.records[myID]` (split by game version, read by the harvest; `myID` is 8 random base32 characters and never appears in the debug report). `ns.SeedData` is the seed written by `npm run harvest`; a record the seed already absorbed starts over at the seed's epoch so nothing counts twice. `CatchDB.Query(mapID, cell, filter)` sums the seed and the own record (or `mine`) for a spot, or for the whole map when the spot has fewer than 50 catches; results are cached until `CatchDB.GetVersion()` changes.
- **UI/**: Indicator (next action, cast bar, session timer, "No bobber" when the soft interact GUID is not game object 35591; while the bobber is still flying, up to 3 s after the channel start, no warning), Settings (canvas pages built from plain widgets, not the Settings setting-type API), StatsFrame (two tabs below the window, the game's `PanelTabButtonTemplate` or plain buttons, the last one saved in `OneKeyFishingDB.statsTab`; the statistics page has rows in `ROWS`, cells keyed by row key; a 1 s tick does a full refresh when `Stats.GetVersion()` changed or the window is marked dirty by `PRICES_CHANGED`, `SETTINGS_CHANGED`, a skill change or item info of a caught item, and otherwise only redraws the time rows, so nothing moves outside fishing mode), CatchHere (the "What can be caught here" page: `CatchDB.Query` for the current place, a skill filter that follows the own range until one is picked by hand and a source filter, both in memory only; redrawn on the 1 s tick when the data, the place or a filter changed; the map and the skill range are read again on zone, loading-screen and skill events, the cell every second), Minimap (the button and the Addon Compartment entry from the TOC), ItemHooks (Alt+Click on items through `HandleModifiedItemClick`, plus a tooltip line), CopyWindow. **Debug.lua** builds the `/okf debug` report.
- **Messages** (`ns.Fire` -> `ns.On`): `MODE_CHANGED` (on/off), `ACTION_STATE` (the key's binding changed), `FISHING_CAST_START` / `FISHING_CAST_STOP`, `FISH_CAUGHT` (items, fromPool, castID) / `FISH_MISSED` (castID; each settles that cast and every earlier one), `LURE_READY`, `SETTINGS_CHANGED`, `GEAR_LIST_CHANGED`, `AUCTION_STATE` (scan progress), `PRICES_CHANGED` (a scan finished or stopped).

## Known API facts for Forever (verified in game)

Signatures (not behaviour) can be checked without the game, in this order:

1. **The live client's own export.** Start the client with `-console` (Battle.net: game settings, additional command line arguments). On the login or character screen, open the console (`` ` ``) and run `exportInterfaceFiles code`. The code lands in `<WoW folder>/_forever_/BlizzardInterfaceCode/Interface/AddOns/`:
   - `Blizzard_APIDocumentationGenerated/*.lua` holds signatures, enums and events;
   - FrameXML shows how Blizzard itself uses an API (`Blizzard_FriendsFrame/Camelot/` is the Forever version of a frame);
   - the client build is in `<WoW folder>/.build.info` (product `wowf`).

   This works without entering the world, so it is available before launch. Re-export after every client patch.
2. **Public dumps** (slightly older builds):
   - the `forever` branch of [Gethe/wow-ui-source](https://github.com/Gethe/wow-ui-source/tree/forever) (`Blizzard_APIDocumentationGenerated`);
   - the global list in [Ketho/BlizzardInterfaceResources](https://github.com/Ketho/BlizzardInterfaceResources/blob/forever/Resources/GlobalAPI.lua);
   - the [1.60.1 API notes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes).

Rules for reading the dumps:

- **Undocumented globals.** Old globals such as `GetLootSourceInfo` and `BNGetNumFriends` are not in the generated docs. For those, check Ketho's GlobalAPI list or a use in FrameXML.
- **Deprecated globals.** Files in `Blizzard_Deprecated*` (`BNSendGameData`, `ChatFrame_AddMessageEventFilter`, ...) load only with the `loadDeprecationFallbacks` CVar. Use the namespaced functions instead (`C_BattleNet.SendGameData`, `ChatFrameUtil.AddMessageEventFilter`).
- **Checked against build 1.60.1.70685 (2026-10-29).** The live export has every API the catch database relies on (`specs/002-local-catch-db/research.md` R11, `specs/003-guild-group-sync/research.md`), including `C_EncodingUtil`, `Enum.SendAddonMessageResult`, `Enum.AddOnRestrictionType` and `PanelTabButtonTemplate`.


- `INTERACTTARGET` exists. The bobber is readable as unit `softinteract` (name and GUID), but it has **no nameplate** and `UnitExists` is false, so nothing can be anchored to it.
- Fishing rank spells are 7620 / 7731 / 7732 / 18248. The skill comes from `GetProfessions()` → `GetProfessionInfo` (skillLine 356); `GetSkillLineInfo` does not exist.
- These are missing: `GetSpellInfo`, `GetItemInfo`, `EquipItemByName` and the classic auction API. Use `C_Spell`, `C_Item`, `C_Item.EquipItemByName` and `C_AuctionHouse` instead.
- `C_Item.EquipItemByName` fails silently while casting or channeling, so a gear swap entry is only cleared on `PLAYER_EQUIPMENT_CHANGED`, and a restore during a cast waits for the cast to end.
- Bags cannot be opened while the Settings panel is open, so items are added through Alt+Click in bags, not from the panel.
- Key bindings on punctuation keys (`'` `;` `[` ...) are named by the character the current Windows keyboard language types, so they break when the language is switched; letters, numbers, F-keys and mouse buttons do not. There is no API for physical keys; the settings and README tell players to bind such keys once per language (two slots per binding).

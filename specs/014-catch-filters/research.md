# Research: Catch Filters by Item Kind

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Date**: 2026-11-16

Every question below is answered from the code, the client export (build 1.60.1.70685,
`BlizzardInterfaceCode/Interface/AddOns`) or the in-game `/run` of 2026-11-16 recorded in the spec's
clarifications. Nothing is left for the game to confirm; the one accepted assumption is R3.

## R1. One term: "kind"

- **Decision**: the code, the saved field, the texts and the documents say **kind** (`ItemKinds`, `Catalog.ItemKind`,
  `settings.hiddenKinds`, "Kinds: all"). The request's working names `GameData/ItemCategories.lua` and
  `CatchDB.ItemCategory` are renamed to match.
- **Rationale**: the spec and the player's button already say "kind"; one word from the data to the button keeps
  searches and reviews simple, and "category" is already the game's word for the addon list (`## Category` in the TOC).
- **Alternatives considered**: "category" everywhere (the spec and the UI would change instead; no gain).

## R2. Where the kind is decided and where the filter applies

- **Decision**:
  - The list of known items and the class rules are data in a new `GameData/ItemKinds.lua` (layer 0).
  - The lookup `Catalog.ItemKind(itemID)`, the ordered kinds `Catalog.KINDS`, the grouping
    `Catalog.Group(items)` and the saved choice (`Catalog.IsKindShown`, `Catalog.SetKindShown`,
    `Catalog.ShownKinds`) live in `Catalog/Catalog.lua` (layer 2).
  - The filter is applied **after** the views: `CatchDB.Query`, `QueryMap`, `QueryCells` and the catalog's index are
    unchanged, and neither `CatchDB.FilterKey` nor any cache key gets a kind part.
- **Rationale**:
  - FR-010 asks that hiding kinds change no chance, count, price or the spot/map choice. Those are all computed by
    the views over every item; a filter applied to the finished item list meets FR-010 by construction, and a filter
    inside `BuildView` would have to be kept out of every sum by hand.
  - A kind part in `FilterKey` would give the catalog one index per kind choice, each built over every map in frame
    steps (`Catalog.lua` "The index"); a player ticking boxes would start a rebuild per click. Applied at read time,
    a click costs one pass over an already sorted list.
  - The catalog already owns item-level questions (names, search, the Poor rule) and is read by both tabs; the catch
    database stays about places and sums. Both are layer 2, so the layer rule is the same either way.
- **Alternatives considered**: `CatchDB.ItemCategory` with `filter.kind` in the views' cache key, as the request
  sketched (rejected for the two reasons above); the lookup in `Core/Data.lua` (layer 0 may not hold a saved player
  choice's logic tied to the catalog, and nothing in Core needs it).

## R3. The kind of an item

- **Decision**: in this order:
  1. `GameData.ItemKinds.byItem[itemID]` (the 31 items of FR-003);
  2. else `C_Item.GetItemInfoInstant(itemID)`'s `classID` and `subClassID` against `GameData.ItemKinds.byClass`: a
     `"<class>:<subclass>"` key first (`"7:8"` -> fish), then a `"<class>"` key (`"7"` -> reagents, `"0"` ->
     potions);
  3. else, and when the instant info is missing (an item the client does not know, V27), `"other"`.

  No result is cached between draws: an unknown item becomes known during the session (`ITEM_DATA_LOAD_RESULT`),
  and the lookup is a table read plus one instant call, cheaper than any cache bookkeeping. Quality is never read
  (FR-005).
- **Rationale**: the in-game facts of 2026-11-16 show the class cannot separate a fish from a clam (7 / 11) or a
  junk fish from a chest (15 / 0), so the list decides the known items; for new items the class is the only
  language-free signal (Principle II). Forever reports the Mainline classes (raw fish is 7 / 8).
- **Accepted assumption**: a new item outside the list may land in a neighbouring kind (a fish of class 7 / 11 under
  Reagents & herbs) or in Other; the list is extended in a later version. No `VERIFY` marker (spec Assumptions).
- **Alternatives considered**: quality (rejected: the junk fish is quality 1, an uncached item has none);
  `C_Item.GetItemSubClassInfo` names as kinds (rejected: the game's words, "Trade Goods", are not the fishing kinds
  the author asked for); tooltip text (rejected: localized, slower, needs the item cached).

## R4. Keeping the list complete

- **Decision**: a test loads the bundled seed and `GameData.FishedContainers` and fails for any item ID missing
  from `GameData.ItemKinds.byItem` (SC-001). `npm run harvest` does not write the list: a new seed item makes the
  test fail, and the author picks its kind in the same change.
- **Rationale**: the seed is regenerated by a tool; a failing test is the cheapest reminder, and the choice of a
  kind is a judgement (a junk-named fish is Fish) a tool should not make.
- **Alternatives considered**: the harvest writing kinds from the class rules (rejected: it would file Oily
  Blackmouth under Reagents); a check in `npm run check` (the test already runs in `npm test`, which the workflow
  requires after every change).

## R5. The saved choice

- **Decision**: `OneKeyFishingDB.settings.hiddenKinds = {}` (account-wide), a set of hidden kind names
  (`{ containers = true }`). Defaults fill the empty table for existing installs (`ApplyDefaults` copies a table
  default); no `DB_SCHEMA` bump. Written only by `Catalog.SetKindShown(kind, shown)`, which fires
  `SETTINGS_CHANGED("hiddenKinds")`; both tabs already mark themselves dirty on `SETTINGS_CHANGED` (`MarkDirty`), but
  that redraws only on the window's next tick (up to a second), so the menu's toggle also calls the shown tab's
  `Refresh` at once (as `SetWater` does; FR-007). An unknown name
  in the set (a kind a later version drops) is ignored; a kind the set does not name is shown (FR-008).
- **Rationale**: storing the hidden kinds, not the shown ones, makes "a new kind is shown" automatic; one setting
  for both views is spec FR-007; account-wide like every other setting.
- **Alternatives considered**: the shown kinds (a new kind would be hidden for everyone who ever chose); per-view
  choices (spec Assumptions: one choice); per character (no reason to differ between characters).

## R6. The kind menu

- **Decision**: a new helper `ns.OpenCheckboxMenu(owner, choices, isChecked, toggle)` in `UI/Widgets.lua`, next to
  `ns.OpenRadioMenu`, using `root:CreateCheckbox(text, isSelected, setSelected)`. In the client export
  (`Blizzard_Menu/MenuTemplates.lua:369-380`) a checkbox element's response is `MenuResponse.Refresh`, so the menu
  stays open and redraws its marks after a click (spec US2 scenario 2). Without `CreateCheckbox` the helper falls
  back to buttons with the check mark, like the radio menu (the menu then closes after a click). The button text is
  "Kinds: all" or "Kinds: %d of %d" (FR-009).
- **Layout**: the statistics window is 580 wide and holds three 150-wide filter buttons (482 with the margins),
  and a button grows to its text (`ns.CreateButton`). A fourth button in that row pushed it past the window's edge
  (595 in English with Water shown; in `frFR` and `esES` even without Water, where "Skill: All skill levels" alone
  is near 300), as the code reviews of 2026-11-16 found. So the Kinds button sits apart at the top right of both
  tabs, on the row of the place's name (shortened to 400) or of the search box (300 wide), and the filter row keeps
  its width; the in-game checklist looks at the longest languages (R11).
- **Rationale**: the same menu system the other filter buttons use; the checkbox template is Blizzard's own.
- **Alternatives considered**: five toggle buttons on the page (no room next to three filter buttons and the search
  box); a radio menu with "Fish only" presets (cannot express "fish and containers").

## R7. Headers in the two lists

- **Decision**:
  - `Catalog.Group(items)` takes a list of rows that carry `itemID` (in the view's order) and returns
    `list, hiddenCount`: `list` is what the tabs draw, `{ header = kind }` before each shown kind's rows in
    `Catalog.KINDS` order, no header for a hidden or empty kind; `hiddenCount` counts the rows left out by the kind
    filter. The order inside a kind is the order of the input (stable).
  - "What can be caught here" (`UI/CatchHere.lua`) fills its fixed rows from the groups: a header row (kind name in
    the header font, no icon, no columns, no tooltip, no click) before each group's items; headers count against
    `MAX_ROWS`, and "and %d more" counts only the items not shown.
  - The catalog (`UI/CatalogTab.lua`) gives its list elements `{ header = kind }` before each group; `InitItemRow`
    draws a header element as a plain label (no icon, no zones, no tooltip, no click). The scroll list keeps one
    element extent, so a header is one row high.
  - The catalog still applies its own rules first (known items, the Poor rule without a search, the search text);
    the kind filter applies to what they let through.
- **Rationale**: one grouping function, tested without frames, serves both tabs; a header as a list element keeps
  the scroll box with one row template and one height.
- **Alternatives considered**: sorting by kind without headers (the spec asks for headers); collapsible groups (not
  asked for; more state).

## R8. The texts of an empty list

- **Decision**:
  - "What can be caught here": when the view has items but `Catalog.Group` leaves none, the page message reads "The
    kind filter hides every item." (FR-011); the counts line and the hints stay as they are.
  - The catalog: when `Catalog.Items` returns rows but all are hidden, the status reads the same text; with a search
    and hidden matches it reads "The kind filter hides the matches." (US3 scenario 2). The present texts ("No item
    matches the search.", "Nothing has been caught yet.") keep their cases, decided before the kind filter.
- **Rationale**: a player must never take a filtered list for missing data (spec US2 scenario 3, FR-011).
- **Alternatives considered**: one text for both cases (the search case reads better with "matches").

## R9. A hidden item opened directly

- **Decision**: `CatalogTab.Show(itemID)` and `Catalog.Places` / `Catalog.Spots` ignore the kind choice; only the list
  (`Catalog.Items` through the tab) is filtered (FR-012). A text argument (`/okf catalog <name>`) fills the search; if
  the one match is hidden by kind, the list shows the "matches" text of R8 and nothing is chosen.
- **Rationale**: a link or tooltip names one item on purpose; a name search is a list operation.
- **Alternatives considered**: choosing a hidden single match by name (would make the search ignore the filter only
  sometimes).

## R10. Tests

- **Decision** (each fails without its change):
  - `tests/catalog/kinds_test.lua`: the list (every FR-003 ID), the class rules (7 / 8, 7 / 11, 0 / 5, 15 / 0, no
    instant info), an item learned mid-session moves from Other, every seed item and fished container listed
    (SC-001), `Group` order, stability, empty and hidden kinds, `hiddenCount`, `SetKindShown` writes the set and fires
    `SETTINGS_CHANGED`, an unknown saved name ignored, a missing kind shown.
  - `tests/ui/here_kinds_test.lua`: headers in order, hidden kinds left out, chances and the scope unchanged with
    hidden kinds (FR-010, SC-004), the empty-by-filter message, "and %d more" with headers.
  - `tests/ui/catalog_kinds_test.lua`: list headers, hidden kinds, the two status texts, a hidden item opened by ID
    shows its places, the choice shared with the catch tab.
  - `tests/gamedata/shape_test.lua`: the shape of `ItemKinds` (every kind name known, every class key well formed).
  - `tests/wow.lua`: `item_classes[itemID] = { classID, subClassID }` makes `C_Item.GetItemInfoInstant` return the
    seven values; the `MenuUtil` stub already records `CreateCheckbox` entries (`menu_entries`).
- **Rationale**: the kinds, the grouping and the saved choice run without the game (Principle V); the two pages are
  covered like the existing `here_page_test.lua` and `catalog_list_test.lua`.

## R11. In-game check

- **Decision**: a short checklist `docs/checklists/catch-filters.md`: the menu stays open while ticking (R6), the
  headers look right in both lists and in the scroll list, the choice survives `/reload` and a relog, a container
  link opens the catalog with Containers hidden. It closes no `VERIFY` marker (there is none); it is the author's
  look at the new UI (Principle IV).
- **Rationale**: the menu response and the list drawing are read from the client export and the stubs; only the game
  shows them.
